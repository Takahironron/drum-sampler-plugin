# 評価の結果（2026-11-16。MIDI だけで鳴らす: キットと MIDI の約束、解析の参照実装、プラグインとの一致）

段階 1 の聞き比べ（`2026-11-16_段階1の確認_v5と直したNMFD.md`）で聞いた `rerender_parts.wav` は方式 C で、**打ごとに元の音の特徴を見て代表音を選び、相互相関で位置を合わせている。どちらも MIDI には無い情報。** プラグインが受け取るのは打の時刻・種類（ノート番号）・強さだけなので、その 3 つだけで鳴らした音を物差しにし直した。測ったのはクラウドの標本（E-GMD 14 本、StemGMD 12 曲。どちらも CC BY 4.0）。区分 A はまだ。

途中で、**E-GMD の正解の MIDI と音の時刻がファイルごとにずれている**ことが分かった（8 節）。この記録の E-GMD の数字は、ずれを直した正解で測り直したもの。

## 1. 決めたこと（キットと MIDI の約束）

解析（Python の `drumeval/extract.py`）と音源（C++ の `SampleEngine`）が同じ決まりで動く。変えるときは両方を変える。

| 項目 | 決まり | 理由 |
|---|---|---|
| 強さ ↔ 音量 | 強さ 1〜127 は、種類ごとの打のピークの範囲に dB で線形（`kit.json` の `level_range_db`）。上限はその曲のその種類の最も大きい打。下限は「上限 − 30 dB」と最も小さい打の小さい方 | 元の打の音量を MIDI で運べる。打が全部同じ大きさの打ち込みの曲でも、DAW で強さを下げれば小さく鳴る |
| 音の選び方 | その種類の代表音のうち、ピークが目標に最も近い音。残りの差は音量で合わせる（持ち上げは +12 dB まで、下げる側は制限なし） | 2 節。従来の「4 段のゾーンから順に選ぶ」より 0.5〜0.7 近い |
| ラウンドロビン | しない（同じ強さなら同じ音） | ±0.5 dB の幅で回しても距離が 0.13〜0.17 増える。音量が近くても、鳴った状況の違う音が混ざる |
| 位置 | 各音は立ち上がりの 2 ms 前から始まる（`lead_sec`）。プラグインは打点から鳴らし始め、2 ms を遅れとしてホストに伝える | 立ち上がりの頭を切らない。ホストが補正するので、並べて置いた元のステムと立ち上がりが重なる |
| チョーク | シンバル以外は、同じ種類の次の打の立ち上がりから 5 ms で前の音を止める | 3 通り（全部／ハイハットだけ／無し）で、わずかに最良（2 節） |
| 打点の合わせ直し | 各打の時刻を、そのパートの音の立ち上がりに ±20 ms の範囲で合わせる（`refine_onsets`） | 採譜の時刻は約 10 ms 刻み。取りこぼしと時刻のずれを入れた打点で、距離が 0.26〜0.31 下がる |
| 音の無い打 | その種類の大きい打より 40 dB 以上小さい打は、MIDI とキットに入れない（`silent_hits`） | 採譜の誤検出のうち、分けたパートに音が無い時刻のもの。3 節 |
| 代表音の候補 | 分離の確からしさ（`nmfd.hit_confidence`）が 0.8 未満の打からは、代表音を取らない | 他の音と重なった打から切り出した音は、大半が別の太鼓の音。7 節 |

## 3. 音の無い打を除く

取りこぼしのある打点に、ランダムな時刻の偽の打を各種類 15% 足して、除く前後の適合率／再現率を測った。

| 下限（その種類の大きい打より） | StemGMD キック | スネア | ハイハット | E-GMD キック | スネア | ハイハット |
|---|---|---|---|---|---|---|
| 除かない | 0.82／0.75 | 0.83／0.73 | 0.82／0.72 | 0.84／0.83 | 0.85／0.82 | 0.81／0.74 |
| **−40 dB（採用）** | 0.85／0.75 | 0.87／0.73 | 0.85／0.72 | 0.87／0.83 | 0.90／0.81 | 0.86／0.73 |
| −30 dB | 0.90／0.75 | 0.90／0.72 | 0.89／0.72 | 0.91／0.83 | 0.94／0.80 | 0.90／0.71 |
| −25 dB | 0.91／0.75 | 0.94／0.69 | 0.91／0.71 | 0.92／0.83 | 0.96／0.79 | 0.92／0.70 |

- −40 dB なら、再現率をほぼ変えずに（E-GMD のスネアとハイハットで −0.01）適合率が 0.03〜0.05 上がる。−30 dB にすると適合率はさらに 0.03〜0.05 上がるが、除かない場合と比べて、スネアの小さい打（ゴーストノート）を 0.01〜0.02、E-GMD のハイハットを 0.03 落とす。安全な側を採った。
- 除けるのは「そのパートに音が無い時刻」の誤検出だけ。別の太鼓の音を取り違えた誤検出（スネアの位置のハイハットなど）は、NMFD がその音の一部をそのパートに入れるので残る。
- シンバルは適合率が 0.5 前後のまま変わらない（原因は未確認。StemGMD の標本でシンバルのある曲は 2 曲だけ）。

## 4. 解析の参照実装

`analysis/analyze_stem.py`（`drumeval/analyzer.py`）が、ステム 1 本からキット（`kit.json` と WAV）と打点の MIDI（`hits.mid`）を作る。段階 2（C++／ONNX への移植）の基準になる。

- 所要時間（Python、クラウドの 4 コア）: 69 秒のステムで 8 秒、180 秒で 26 秒（採譜を除く。ほぼ全部が NMFD）。最大メモリ 2.2 GB。採譜（ONNX）の時間はまだ足していない（要確認）が、**M1 の目安「3 分の曲を 1 分以内」には、Python の参照実装の時点で届く見込み。** Takahiro の PC での時間は `analysis.json` の `timings_sec` に出る。
- 例（StemGMD の s02、正解の打点、37.5 秒）: キック 71、スネア 124、ハイハット 137 打。音が無くて除いた打 2。分離の確からしさの中央値は キック 1.00、スネア 0.93、ハイハット 0.76。

## 5. プラグインとの一致

- `plugin/Source/SampleEngine.cpp` を上の約束に合わせた（4 段のゾーンとラウンドロビン、強さによる余分な減衰をやめた）。
- 同じキットと同じ打点（サンプル位置・ノート番号・強さ）から、C++ のエンジン（`KitRenderTest --events`）と Python の `render_midi` が出す音を 1 サンプル単位で比べる（`analysis/engine_parity.py`）。**差の最大は、デモのキットで 4.8e-07（ピーク 3.0）、E-GMD と StemGMD から作ったキットで 4.5e-08〜1.2e-07。** 32 bit float の丸めの範囲。
- CI: `build.yml` の Linux のジョブ（プラグイン側を変えたとき）と `engine-parity.yml`（Python の参照実装を変えたとき）で毎回比べる。Windows の pluginval（強さ 5）と、Linux の pluginval（画面のテストを除く）は SUCCESS。
- つまり、**`rerender_midi.wav`（Python）を聞けば、プラグインで鳴る音を聞いたことになる。**

## 6. 残る差の内訳（MIDI だけ と 方式 C）

MIDI だけと方式 C の差を、選び方と位置を別々に差し替えて測った（1 曲 40 秒、24 音）。

| | StemGMD 正解 | StemGMD 取りこぼしあり | E-GMD 正解 | E-GMD 取りこぼしあり |
|---|---|---|---|---|
| MIDI だけ（種類ごとに 1 つのノート） | 1.149 | 1.552 | 0.942 | 1.205 |
| ＋ 位置を相互相関で合わせる（診断用） | 1.043 | 1.514 | 0.883 | 1.166 |
| 方式 C の選び方、位置は MIDI どおり | 0.985 | 1.254 | 0.768 | 0.923 |
| 方式 C（選び方 ＋ 位置合わせ） | 0.878 | 1.200 | 0.695 | 0.874 |
| 種類の中を特徴で 2 つに分け、別のノートにする | 1.032 | 1.398 | 0.875 | 1.037 |
| 3 つに分ける | 0.977 | 1.333 | 0.800 | 1.011 |
| 4 つに分ける | 0.975 | 1.279 | 0.778 | 0.992 |
| 6 つに分ける | 0.967 | 1.253 | 0.772 | 0.947 |

- 差の大半は音の選び方（0.16〜0.30）で、位置合わせは小さい（0.04〜0.11）。
- 種類の中を、音量によらない特徴（減衰、明るさ、帯域の配分）の k-means で 3 つに分けて別の MIDI ノートにすると、距離は 0.14〜0.22 下がる。効くのはほとんどハイハット（StemGMD の正解の打点で、ハイハットだけ分けて −0.12、キックだけ −0.05、スネアだけ −0.00）。
- **しかし、分けた群は奏法ではなかった。** StemGMD の正解の MIDI には細かい種類（ハイハットの開・閉・ペダル、サイドスティックなど）があるので比べると、群の純度は「最も多い種類の割合」と同じで（例: s02 のハイハットは 閉 117・開 10・ペダル 10 で、純度 0.85 = 最多の割合 0.85）、開閉を見分けていない。群を分けていたのは **「スネアと同時に鳴ったハイハット」「キックと同時」「単独」という文脈**と、音量、次の打までの長さだった（s02 と s11 では、3 群のうち 1 群が「97〜100% がスネアと同時」）。
- **採らない。** 意味の分からないノートが種類ごとに 3 つできると、DAW で編集できず、新しいパターンを打ち込むときにどれを使えばよいか決まらない。奏法の分類（開閉、ライドとクラッシュ、タムの高さ）は、計画書どおり Phase 2 の「細かい分類」で、正解のある学習で行う。
- 方式 C の距離が良いのは、「スネアと同時のハイハット」には同じ文脈から切り出した音を当てているから、という面がある。**方式 C の距離は、キットの質の物差しとしては甘い。**

## 7. キットの音の純度と、分離の確からしさ

6 節の群が「文脈」だったので、同時に鳴る打で分離がどれだけ崩れるかを、StemGMD の本当のパート別録音で直接測った（正解の打点、打点から 60 ms の区間、打ごとの SN 比 = 本当の音 ÷ 取り出した音との差）。

| パート | 単独 | キックと同時 | スネアと同時 | ハイハットと同時 |
|---|---|---|---|---|
| キック | +39.7 dB | — | +28.7 dB | +35.0 dB |
| スネア | +15.8 dB | +5.9 dB | — | +24.2 dB |
| ハイハット | +9.4 dB | +7.4 dB | **+2.4 dB** | — |

- **スネアと同時に鳴ったハイハットは、取り出した音の約半分が別の音**（SN 比の中央値 +2.4 dB。11% は 0 dB 未満）。ハイハットの打の 25% がこれに当たる。
- そのまま代表音にしていたので、**キットのハイハットの代表音の 31〜33% が「SN 比 3 dB 未満」（ほぼ別の太鼓の音）だった。** 再現の距離には出ない（同じ文脈で使えば帳尻が合う）が、ハイハットだけを聞いたり、新しいパターンを鳴らしたりすると、スネアの混ざったハイハットが鳴る。
- **分離の確からしさ**（`nmfd.hit_confidence`）: 打点から 60 ms の間の Wiener マスクの値の平均（そのパートの取り分で重み付け）。正解が無くても計算できる。打ごとの SN 比との順位相関は キック 0.78、スネア 0.91、ハイハット 0.92。「SN 比 3 dB 未満の打」を見分ける AUC は 0.96〜1.00。
- **確からしさの低い打からは代表音を取らない**ことにした（`extract.confident_segments`。下限は 0.8 と、その種類の中央値の小さい方）。

| ハイハットの代表音（StemGMD、24 音） | 純度の中央値 | SN 比 3 dB 未満の割合 |
|---|---|---|
| 選ばない（今まで）。正解の打点／取りこぼしあり | 6.7／6.5 dB | 31%／33% |
| 下限 0.5 | 7.9／7.5 dB | 16%／16% |
| 下限 0.65 | 8.4／9.1 dB | 9%／7% |
| **下限 0.8（採用）** | 9.5／9.9 dB | **1%／3%** |

- スネアは 3% → 0%、キックは元から 0%。音の数はほとんど減らない（24 → 23）。
- 再現の距離への影響（StemGMD、`run_eval.py --parts nmfd-oracle`）: MIDI だけ 1.149 → **1.131**。方式 C は 0.884 → 0.926 と少し悪くなる（文脈の合う「混ざった音」を使えなくなるため。6 節の最後の点）。E-GMD でも同じ向き（正解のずれを直す前の測定で、MIDI だけ 1.298 → 1.276、方式 C 0.898 → 0.923）。
- 重なった打も、打点（MIDI）と強さには残る。強さは重なりの分だけ狂う（スネアと同時のハイハットは、中央値で 2.1 dB 小さく測られる）。
- 確からしさは `kit.json` の各音（`confidence`）と `analysis.json`（`confidence_median`）に書く。計画書の「信頼度表示」（Phase 2）の材料になる。
- パートごとに本当の録音と比べると（−40 dB の共通の雑音を足した距離）、切り出す前のパートそのものの距離が キック 0.23、スネア 0.41、**ハイハット 1.37**。ハイハットは選び方の前に、分離そのものが弱い（持ち越し 8）。

## 8. E-GMD の正解の時刻のずれ

**見つけた経緯**: E-GMD の e08（Studio (Live Room)）で、スネアの確からしさの中央値が 0.00 だった。調べると、大きいスネアの音がスネアのパートではなくハイハットのパートと残差に入っていた。原因は分離ではなく、**正解の MIDI と音が 73 ms ずれていた**こと（音の方が早い）。

**測り方**（`analysis/drumeval/align.py` の `label_offset`）: 音の立ち上がりの強さ（対数で圧縮したスペクトルの増加分。約 1.5 ms 刻み）と、打点に 1 を立てた列の相互相関が最大になるずれ（±250 ms）。別の測り方（キックとスネアの打点から、最も近い音の立ち上がりまでの差の中央値）と、67 本中 66 本で 6 ms 以内に一致した。ずれは 1 本の中では一定（e08 は前半 −72.9 ms、後半 −73.0 ms）。

**分布**（E-GMD の 67 本。test 分割から 14 本、train 分割から 53 本。43 キット）:

| | 10 ms 以上 | 20 ms 以上 | 30 ms 以上 | 50 ms 以上 | 範囲 |
|---|---|---|---|---|---|
| 67 本 | 34% | 21% | 15% | 7% | −73〜+119 ms |
| うち train の 53 本 | 25% | 15% | 9% | 6% | −44〜+119 ms |
| うち test の 14 本 | 71% | 43% | 36% | 14% | −73〜+61 ms |

- 取得スクリプトは元のファイルをそのまま写しているので、**E-GMD の配布物そのもののずれ**。StemGMD の 12 曲は 0〜+1 ms。
- キットごとに決まった値ではない（例: Studio (Live Room) は −73 ms と +0.5 ms、Big Room (Layered) は −44・+12・+52 ms、Cassette は +61・−21 ms）。ファイルごとに測る必要がある。
- test 分割の標本の方がずれが多い（14 本と少ないので、割合は目安）。

**クラウドの数字への影響**（`run_eval.py --parts nmfd-oracle`、E-GMD 14 本、1 曲 60 秒）:

| | 方式 C | MIDI だけ | MIDI だけ、48 音 | 自己再現 |
|---|---|---|---|---|
| 配布物のままの正解 | 0.923 | 1.276 | 1.170 | 0.205 |
| ずれを直した正解 | 0.746 | 0.959 | 0.863 | 0.118 |

- 大きく変わった曲: e05（−44 ms）MIDI だけ 2.03 → 1.11・自己再現 0.64 → 0.06、e08（−73 ms）2.23 → 1.04・0.86 → 0.24、e03（+32 ms）1.34 → 0.77、e11（+61 ms）1.30 → 0.88、e10（−33 ms）1.50 → 0.93。e05 と e08 の自己再現が悪かったのは残響のせいではなかった。
- 30 ms のずれで、パート分けから後の全部が崩れる（打点の合わせ直しは ±20 ms まで）。**採譜モデルの打点の時刻が 20 ms 以上ずれると、製品の経路でも同じことが起きる。**

**採譜モデルへの影響（未確認。Takahiro の PC で確かめる）**:

- 学習（v1〜v5）は、ずれたラベルを使っている。ラベルは 10 ms 刻みで、打点とその次のフレームを 1 にする。train の標本の 25% は、ラベルが 1 フレーム以上ずれている。
- E-GMD の test での採点（許容 ±50 ms）は、50 ms 以上ずれたファイル（標本の 7〜14%）では正しい検出をほぼ全部誤りと数え、30〜50 ms のファイルでも一部を落とす。**M0-1 の「0.77」（E-GMD test）は低く出ている恐れがある。** 検証（0.85）と test（0.77）の差（持ち越し 1）も、分割ごとのずれの違いで説明できるかもしれない。

**作った道具**:

## 9. 製品に入れる採譜モデル（v6）の準備

v5 は、学習の増強（にじみ）に区分 A の CD 曲のステムを使ったので、製品に入れられない（R3）。v6 は次の 2 点を変える。

1. **正解の時刻のずれを直す**（8 節）。
2. **にじみを自作の合成音にする**（`analysis/make_bleed_set.py`、`drumeval/bleed.py`）。ベース、撥弦（Karplus–Strong）、鍵盤、パッド、リード、声の母音と子音（子音はハイハットと取り違えやすい音）を合成し、テンポ・調・コード進行・編成を乱数で決める。音声の素材も、既存の曲の MIDI も使わない。60 分ぶんを 1 分ほどで作れる。

- にじみの候補として Slakh2100／BabySlakh（CC BY 4.0）も調べた（`ライセンス一覧.md` #15）。元の MIDI が既存曲の打ち込みなので、まず合成音だけで作り、足りなければ検討する。
- v5 は、にじみに区分 A そのもののステムを使っていた（評価に使う曲の、ドラム以外の音を学習で見ている）。区分 A での v5 の数字は、その分だけ有利だった可能性がある。v6 の区分 A の数字が、初めての「見ていない曲」での数字になる。
- 合成音のにじみが、実際の分離の残りにどれだけ近いかは分からない（中〜高域の成分が少ない）。v6 が区分 A で v5 より悪ければ、まずここを疑う。
