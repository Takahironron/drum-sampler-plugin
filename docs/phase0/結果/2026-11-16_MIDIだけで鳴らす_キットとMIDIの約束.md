# 評価の結果（2026-11-16。MIDI だけで鳴らす: キットと MIDI の約束、解析の参照実装、プラグインとの一致）

段階 1 の聞き比べ（`2026-11-16_段階1の確認_v5と直したNMFD.md`）で聞いた `rerender_parts.wav` は方式 C で、**打ごとに元の音の特徴を見て代表音を選び、相互相関で位置を合わせている。どちらも MIDI には無い情報。** プラグインが受け取るのは打の時刻・種類（ノート番号）・強さだけなので、その 3 つだけで鳴らした音を物差しにし直した。測ったのはクラウドの標本（E-GMD 14 本、StemGMD 12 曲。どちらも CC BY 4.0）。区分 A はまだ。

## 1. 決めたこと（キットと MIDI の約束）

解析（Python の `drumeval/extract.py`）と音源（C++ の `SampleEngine`）が同じ決まりで動く。変えるときは両方を変える。

| 項目 | 決まり | 理由 |
|---|---|---|
| 強さ ↔ 音量 | 強さ 1〜127 は、種類ごとの打のピークの範囲に dB で線形（`kit.json` の `level_range_db`）。上限はその曲のその種類の最も大きい打。下限は「上限 − 30 dB」と最も小さい打の小さい方 | 元の打の音量を MIDI で運べる。打が全部同じ大きさの打ち込みの曲でも、DAW で強さを下げれば小さく鳴る |
| 音の選び方 | その種類の代表音のうち、ピークが目標に最も近い音。残りの差は音量で合わせる（持ち上げは +12 dB まで、下げる側は制限なし） | 下の 2 節。従来の「4 段のゾーンから順に選ぶ」より 0.5〜0.7 近い |
| ラウンドロビン | しない（同じ強さなら同じ音） | ±0.5 dB の幅で回しても距離が 0.13〜0.17 増える。音量が近くても奏法の違う音が混ざる |
| 位置 | 各音は立ち上がりの 2 ms 前から始まる（`lead_sec`）。プラグインは打点から鳴らし始め、2 ms を遅れとしてホストに伝える | 立ち上がりの頭を切らない。ホストが補正するので、並べて置いた元のステムと立ち上がりが重なる |
| チョーク | シンバル以外は、同じ種類の次の打の立ち上がりから 5 ms で前の音を止める | 3 通り（全部／ハイハットだけ／無し）で、わずかに最良（下の 2 節） |
| 打点の合わせ直し | 各打の時刻を、そのパートの音の立ち上がりに ±20 ms の範囲で合わせる（`refine_onsets`） | 採譜の時刻は約 10 ms 刻み。取りこぼしと時刻のずれを入れた打点で、距離が 1.79 → 1.53 |
| 音の無い打 | その種類の大きい打より 40 dB 以上小さい打は、MIDI とキットに入れない（`silent_hits`） | 採譜の誤検出のうち、分けたパートに音が無い時刻のもの。下の 3 節 |

## 2. 鳴らし方ごとの距離

多重解像度 STFT 距離（音量をそろえた後、小さいほど元に近い）。1 曲 40 秒、代表音は種類ごとに 24 音。「取りこぼしあり」は、正解の打点から打を抜き、時刻をずらして、採譜モデルの打点に似せたもの。

| 鳴らし方 | StemGMD 正解の打点 | StemGMD 取りこぼしあり | E-GMD 正解の打点 | E-GMD 取りこぼしあり |
|---|---|---|---|---|
| 自己再現（各打をその打自身の区間で鳴らす。下限） | 0.088 | 0.315 | 0.156 | 0.257 |
| 方式 C（元の音の特徴で選び、相互相関で位置を合わせる。MIDI に無い情報を使う） | 0.884 | 1.195 | 0.861 | 1.044 |
| **MIDI だけ（今回の約束）** | **1.144** | **1.534** | **1.249** | **1.507** |
| MIDI だけ、打点の合わせ直しなし | 1.104 | 1.792 | 1.223 | 1.544 |
| MIDI だけ、近い 3 音を順に使う | 1.312 | 1.793 | 1.471 | 1.864 |
| 従来のプラグインの鳴らし方（4 段のゾーン、順に選ぶ、強さで余分に下げる、ハイハットだけチョーク） | 1.652 | 2.182 | 1.847 | 2.243 |

- **従来のプラグインの鳴らし方は、方式 C より 0.8〜1.2 遠かった。** 段階 1 で聞いた音のままには鳴っていなかった。今回の約束で 0.5〜0.7 縮み、方式 C との差は 0.26〜0.46。
- 打点の合わせ直しは、正解の打点（もともと正確）ではわずかに悪くし（+0.03〜0.04）、ずれのある打点では大きく効く（StemGMD −0.26、E-GMD −0.04）。採譜モデルの打点は後者なので入れる。正解の打点で悪くなる分は、立ち上がりの決め方の粗さで、直す余地がある。
- 帯域の差（MIDI だけ − 元、音量をそろえた後）は、平均でどの帯域も ±0.6 dB 以内。「こもり」は出ていない。

細かい条件（取りこぼしありの打点）:

|---|---|---|---|---|
| 方式 C | 1.195 | 1.000 | 1.044 | 0.847 |
| MIDI だけ（チョーク: シンバル以外） | 1.534 | 1.346 | 1.507 | 1.296 |
| チョーク: ハイハットだけ | 1.554 | 1.358 | 1.526 | 1.318 |
| チョーク: 無し | 1.562 | 1.372 | 1.547 | 1.334 |
| 近い音を順に使う。幅 ±0.5 dB | 1.659 | 1.546 | 1.679 | 1.563 |
| 幅 ±1 dB | 1.719 | 1.590 | 1.765 | 1.629 |
| 幅 ±2 dB | 1.738 | 1.606 | 1.814 | 1.662 |

- 代表音を 48 音にすると、MIDI だけの距離は 0.19〜0.21 下がる（方式 C も同じだけ下がる）。既定の 24 音を増やすかは、区分 A の聞き比べで決める（`--kit-size 48`）。

## 3. 音の無い打を除く

取りこぼしのある打点に、ランダムな時刻の偽の打を各種類 15% 足して、除く前後の適合率／再現率を測った。

| 下限（その種類の大きい打より） | StemGMD キック | スネア | ハイハット | E-GMD キック | スネア | ハイハット |
|---|---|---|---|---|---|---|
| 除かない | 0.82／0.75 | 0.83／0.73 | 0.82／0.72 | 0.84／0.83 | 0.85／0.81 | 0.81／0.74 |
| **−40 dB（採用）** | 0.85／0.75 | 0.87／0.73 | 0.85／0.72 | 0.86／0.83 | 0.89／0.81 | 0.85／0.73 |
| −30 dB | 0.90／0.75 | 0.90／0.72 | 0.89／0.72 | 0.90／0.82 | 0.92／0.78 | 0.88／0.71 |
| −25 dB | 0.91／0.75 | 0.94／0.69 | 0.91／0.71 | 0.91／0.82 | 0.93／0.75 | 0.90／0.69 |

- −40 dB なら、再現率をほぼ変えずに（E-GMD のハイハットだけ −0.01）適合率が 0.02〜0.04 上がる。−30 dB にすると適合率はさらに 0.03〜0.05 上がるが、スネアの小さい打（ゴーストノート）を 0.01〜0.03 落とす。安全な側を採った。
- 除けるのは「そのパートに音が無い時刻」の誤検出だけ。別の太鼓の音を取り違えた誤検出（スネアの位置のハイハットなど）は、NMFD がその音の一部をそのパートに入れるので残る。
- シンバルは適合率が 0.5 前後のまま変わらない（原因は未確認。StemGMD の標本でシンバルのある曲は 2 曲だけ）。

## 4. 解析の参照実装

`analysis/analyze_stem.py`（`drumeval/analyzer.py`）が、ステム 1 本からキット（`kit.json` と WAV）と打点の MIDI（`hits.mid`）を作る。段階 2（C++／ONNX への移植）の基準になる。

- 所要時間（Python、クラウドの 4 コア）: 69 秒のステムで 8 秒、180 秒で 26 秒（採譜を除く。ほぼ全部が NMFD）。最大メモリ 2.2 GB。採譜（ONNX）の時間はまだ足していない（要確認）が、**M1 の目安「3 分の曲を 1 分以内」には、Python の参照実装の時点で届く見込み。** Takahiro の PC での時間は `analysis.json` の `timings_sec` に出る。
- E-GMD の e14（正解の打点、69 秒）: キック 100、スネア 95、ハイハット 72、タム 38、シンバル 156 打。音が無くて除いた打 7。MIDI だけで鳴らした距離 1.27。

## 5. プラグインとの一致

- `plugin/Source/SampleEngine.cpp` を上の約束に合わせた（4 段のゾーンとラウンドロビン、強さによる余分な減衰をやめた）。
- 同じキットと同じ打点（サンプル位置・ノート番号・強さ）から、C++ のエンジン（`KitRenderTest --events`）と Python の `render_midi` が出す音を 1 サンプル単位で比べる（`analysis/engine_parity.py`）。**差の最大は、デモのキットで 4.8e-07（ピーク 3.0）、E-GMD の e14 から作ったキットで 4.5e-08（ピーク 0.47）。** 32 bit float の丸めの範囲。
- CI: `build.yml` の Linux のジョブ（プラグイン側を変えたとき）と `engine-parity.yml`（Python の参照実装を変えたとき）で毎回比べる。Linux の pluginval（強さ 5、画面のテストを除く）は SUCCESS。
- つまり、**`rerender_midi.wav`（Python）を聞けば、プラグインで鳴る音を聞いたことになる。**

## 6. 残る差の内訳（MIDI だけ と 方式 C）

MIDI だけと方式 C の差（0.26〜0.46）を、選び方と位置を別々に差し替えて測った（1 曲 40 秒、24 音）。

| | StemGMD 正解 | StemGMD 取りこぼしあり | E-GMD 正解 | E-GMD 取りこぼしあり |
|---|---|---|---|---|
| MIDI だけ（種類ごとに 1 つのノート） | 1.149 | 1.552 | 1.246 | 1.512 |
| ＋ 位置を相互相関で合わせる（診断用） | 1.043 | 1.514 | 1.184 | 1.470 |
| 方式 C の選び方、位置は MIDI どおり | 0.985 | 1.254 | 0.891 | 1.069 |
| 方式 C（選び方 ＋ 位置合わせ） | 0.878 | 1.200 | 0.832 | 1.012 |
| 種類の中を特徴で 2 つに分け、別のノートにする | 1.032 | 1.398 | 1.105 | 1.256 |
| 3 つに分ける | 0.977 | 1.333 | 1.020 | 1.206 |
| 4 つに分ける | 0.975 | 1.279 | 1.012 | 1.160 |
| 6 つに分ける | 0.967 | 1.253 | 1.009 | 1.126 |

- 差の大半は音の選び方（0.16〜0.44）で、位置合わせは小さい（0.04〜0.11）。
- 種類の中を、音量によらない特徴（減衰、明るさ、帯域の配分）の k-means で 3 つに分けて別の MIDI ノートにすると、距離は 0.17〜0.31 下がる。効くのはほとんどハイハット（StemGMD の正解の打点で、ハイハットだけ分けて −0.12、キックだけ −0.05、スネアだけ −0.00）。
- **しかし、分けた群は奏法ではなかった。** E-GMD と StemGMD の正解の MIDI には細かい種類（ハイハットの開・閉・ペダル、サイドスティックなど）があるので比べると、群の純度は「最も多い種類の割合」と同じで（例: s02 のハイハットは 閉 117・開 10・ペダル 10 で、純度 0.85 = 最多の割合 0.85）、開閉を見分けていない。群を分けていたのは **「スネアと同時に鳴ったハイハット」「キックと同時」「単独」という文脈**と、音量、次の打までの長さだった（s02 と s11 では、3 群のうち 1 群が「97〜100% がスネアと同時」）。
- **採らない。** 意味の分からないノートが種類ごとに 3 つできると、DAW で編集できず、新しいパターンを打ち込むときにどれを使えばよいか決まらない。奏法の分類（開閉、ライドとクラッシュ、タムの高さ）は、計画書どおり Phase 2 の「細かい分類」で、正解のある学習で行う。
- 方式 C の距離が良いのは、「スネアと同時のハイハット」には同じ文脈から切り出した音を当てているから、という面がある。**方式 C の距離は、キットの質の物差しとしては甘い。**

## 7. キットの音の純度と、分離の確からしさ

6 節の群が「文脈」だったので、同時に鳴る打で分離がどれだけ崩れるかを、StemGMD の本当のパート別録音で直接測った（正解の打点、打点から 60 ms の区間、打ごとの SN 比 = 本当の音 ÷ 取り出した音との差）。

| パート | 単独 | キックと同時 | スネアと同時 | ハイハットと同時 |
|---|---|---|---|---|
| キック | +39.7 dB | — | +28.7 dB | +35.0 dB |
| スネア | +15.8 dB | +5.9 dB | — | +24.2 dB |
| ハイハット | +9.4 dB | +7.4 dB | **+2.4 dB** | — |

- **スネアと同時に鳴ったハイハットは、取り出した音の約半分が別の音**（SN 比の中央値 +2.4 dB。11% は 0 dB 未満）。ハイハットの打の 25% がこれに当たる。
- そのまま代表音にしていたので、**キットのハイハットの代表音の 31〜33% が「SN 比 3 dB 未満」（ほぼ別の太鼓の音）だった。** 再現の距離には出ない（同じ文脈で使えば帳尻が合う）が、ハイハットだけを聞いたり、新しいパターンを鳴らしたりすると、スネアの混ざったハイハットが鳴る。
- **分離の確からしさ**（`nmfd.hit_confidence`）: 打点から 60 ms の間の Wiener マスクの値の平均（そのパートの取り分で重み付け）。正解が無くても計算できる。打ごとの SN 比との順位相関は キック 0.78、スネア 0.91、ハイハット 0.92。「SN 比 3 dB 未満の打」を見分ける AUC は 0.96〜1.00。
- **確からしさの低い打からは代表音を取らない**ことにした（`extract.confident_segments`。下限は 0.8 と、その種類の中央値の小さい方）。

| ハイハットの代表音（StemGMD、24 音） | 純度の中央値 | SN 比 3 dB 未満の割合 |
|---|---|---|
| 選ばない（今まで）。正解の打点／取りこぼしあり | 6.7／6.5 dB | 31%／33% |
| 下限 0.5 | 7.9／7.5 dB | 16%／16% |
| 下限 0.65 | 8.4／9.1 dB | 9%／7% |
| **下限 0.8（採用）** | 9.5／9.9 dB | **1%／3%** |

- スネアは 3% → 0%、キックは元から 0%。音の数はほとんど減らない（24 → 23）。
- 再現の距離への影響（`run_eval.py --parts nmfd-oracle`、1 曲 60 秒）: MIDI だけ StemGMD 1.149 → **1.131**、E-GMD 1.298 → **1.276**。方式 C は 0.884 → 0.926、0.898 → 0.923 と少し悪くなる（文脈の合う「混ざった音」を使えなくなるため。6 節の最後の点）。代表音 48 音なら MIDI だけ 1.031／1.170。
- 重なった打も、打点（MIDI）と強さには残る。強さは重なりの分だけ狂う（スネアと同時のハイハットは、中央値で 2.1 dB 小さく測られる）。
- 確からしさは `kit.json` の各音（`confidence`）と `analysis.json`（`confidence_median`）に書く。計画書の「信頼度表示」（Phase 2）の材料になる。
- パートごとに本当の録音と比べると（−40 dB の共通の雑音を足した距離）、切り出す前のパートそのものの距離が キック 0.23、スネア 0.41、**ハイハット 1.37**。ハイハットは選び方の前に、分離そのものが弱い（持ち越し 8）。

## 8. E-GMD の正解の時刻のずれ（確からしさの値から見つかった）

E-GMD の e08（studioliveroom）で、スネアの確からしさの中央値が 0.00 だった。調べると、大きいスネアの音がスネアのパートではなくハイハットのパートと残差に入っていた。原因は分離ではなく、**正解の MIDI と音が約 73 ms ずれていた**こと（音の方が早い）。標本 14 本を、音の立ち上がりの強さと MIDI の打点の相互相関で測ると:

| ずれ（音 − MIDI） | 本 |
|---|---|
| ±5 ms 以内 | e04、e06、e09、e12 |
| +13〜+17 ms | e01、e02、e13、e14 |
| +25〜+32 ms | e07、e03 |
| −33 ms、−44 ms、−73 ms | e10、e05、e08 |
| +62 ms | e11 |

- ずれは 1 本の中では一定（e08 は前半 −71.8 ms・後半 −72.4 ms）。取得スクリプトは元のファイルをそのまま写しているので、E-GMD の配布物そのもののずれ。StemGMD の 12 曲は 0〜+12 ms。
- **影響**: (1) この記録の E-GMD の数字のうち、e03・e05・e07・e08・e10・e11 は、ずれた打点を「正解の打点」として使っている（打点の合わせ直しは ±20 ms まで）。e05 と e08 の自己再現が悪い（0.64、0.86）のは、残響ではなくこれが主因の疑い。(2) **採譜モデルの学習（v1〜v5）は、このずれたラベルを使っている。** E-GMD の test での採点（許容 ±50 ms）も、ずれの大きいファイルでは正しい検出を誤りと数える。M0-1 の「0.77」は低く出ている恐れがある。
- 次の作業にする: ファイルごとのずれを測って直す道具を作り、標本の正解を直して測り直す。全データでのずれの分布と、v5 を直した正解で採点し直すのは Takahiro の PC で（E-GMD の全体が要る）。
