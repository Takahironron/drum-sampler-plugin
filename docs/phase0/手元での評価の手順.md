# 手元（Windows）で評価を走らせる手順

分離したステムを PC から出さずに、3 指標の表を作るまでの手順。所要は初回 20〜30 分（Python の導入込み）。

## 1. 道具を入れる（初回だけ）

1. **Git for Windows**: https://git-scm.com/download/win から入れる（既に入っていれば不要。PowerShell で `git --version` が出れば入っている）。
2. **Python 3.10 以上**: https://www.python.org/downloads/windows/ から入れる。インストーラーの最初の画面で **「Add python.exe to PATH」にチェック**を入れる。PowerShell で `python --version` が出れば入っている。

## 2. リポジトリを取る（初回だけ）

PowerShell を開き、置きたい場所（例: `D:\Music`）で次を実行する。

```
cd D:\Music
git clone https://github.com/Takahironron/drum-sampler-plugin.git
cd drum-sampler-plugin
git checkout claude/funny-pascal-pmmnoh
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r analysis\requirements.txt
```

- `Activate.ps1` が「スクリプトの実行が無効」で止まったら、`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` を一度実行してからやり直す。
- 2 回目以降は `cd D:\Music\drum-sampler-plugin` → `.\.venv\Scripts\Activate.ps1` だけでよい。
- 最新を取り込むときは `git pull`。

## 3. ステムを置く

分離したドラムのステム（WAV）を次の形に置く。`data\` はコミットされない（`.gitignore` 済み）。

```
data\stems\a01\drums.wav
data\stems\a02\drums.wav
...
data\stems\a10\drums.wav
```

- 曲 ID と曲の対応は `docs\phase0\評価用ステム一覧.md` の区分 A の表。
- SpectraLayers の書き出し（`drum.wav` と他の楽器の WAV、キック.wav などのパート別ステム）をフォルダごと置いてもよい。`drum.wav` を自動で選び、パート別ステムがあれば疑似的な正解として使う。
- 長さはそのままでよい。評価は「ドラムが鳴り始める位置」を自動で見つけて、そこから 60 秒を使う（表の「開始秒」。キックとスネアのパート別ステムがあればその合計で判定）。他の楽器の残りが大きい曲では誤ることがあるので、**前奏が長い曲は曲フォルダに `start.txt`（秒を 1 つ書く。例: a04 なら `71`）を置く**のが確実。`--start` で全曲一律にもできる。`--max-seconds 0` で全部。
- 分離した WAV がまとめて 1 つのフォルダにあるなら、次で自動的に上の形にできる（モノラル FLAC、先頭 90 秒。ファイル名を `a01_...` で始め、開始秒を `@45` のように付けられる）。

```
python analysis\pack_stems.py <分離したWAVのフォルダ> data\stems --seconds 90
```

## 4. 評価を走らせる

```
pip install onnxruntime
python analysis\run_eval.py data\stems --model analysis\models\crnn_synth_v0.onnx --threshold 0.3 --render --out data\results\YYYY-MM-DD.md
```

- `--model` は合成データで学習した小さな採譜モデル（ONNX）。付けなければ学習なしの基準値で推定する。`--threshold` は打点のしきい値（既定 0.5。実ステムでは 0.3 の方が取りこぼしが減る見込み）。
- パート別ステムがある曲では、疑似正解を `hits_pseudo.csv` と `hits_pseudo.mid` に書く。MIDI を DAW に読み込み（120 BPM、1 小節目の頭 = 0 秒）、`original_cut.wav` と並べると、疑似正解の誤りを目と耳で確かめられる。
- `--tag v5` のように印を付けると、書き出す WAV の名前の末尾に付く（`rerender_parts_v5.wav`、`rerender_self_v5.wav`、`nmfd_kick_v5.wav`、`hits_model_v5.mid`）。モデルや設定を替えた結果を上書きせずに並べて聞ける。`original_cut.wav` には付かない。
- 疑似正解（`hits_pseudo.csv`）は実行のたびに書き直される。2026-11-15 に打点の拾い方を作り直した（それまではキックを約 3 倍に数え過ぎていた）ので、それより前の表の「正解の打」と F 値とは比べられない。表の「疑似正解の打の大きさ」の列は、種類ごとに 0〜−10／−10〜−20／−20〜−30 dB の打の数。右側が多い種類は、漏れを打として数えている恐れがある。
- 評価の道具は、自分が曲フォルダに書き出した音（`rerender*`、`original_cut*`、`nmfd_*`、`synthkit_*`、`kit_parts_audition*`、`--save-kit` のフォルダの中身）を、ドラムのステム・パート別ステム・にじみ用の音（`--bleed-dir`）として拾わない。`--render` は同じ名前で上書きするので、前の実行の音を残したいときは **`rerender` で始まる名前**で同じフォルダにコピーしておく（例: `rerender_parts_ft_v5.wav`）。
- `--render` を付けると、各曲のフォルダに聞き比べ用の WAV ができる: `original_cut.wav`（元、同じ長さ）、`rerender_mix.wav`（混ざったドラムから切り出したキットで鳴らし直し）、`rerender_parts.wav`（パート別ステムから切り出したキットで鳴らし直し。パート別ステムがある曲だけ）。
- 1 曲 30〜60 秒ほどで、`--out` の Markdown に表ができる。このファイルをチャットに添付するか、中身を貼る。**出力先は `data\results\` にする**（`docs\phase0\` に出すと、こちらがコミットする記録と名前がぶつかって `git pull` が止まる）。
- **`rerender_midi.wav` が、プラグインで実際に鳴る音**（2026-11-16 から）。MIDI 用のキット（製品のキット）を、打の時刻・種類・強さ（MIDI にある情報）だけで鳴らしたもの。`rerender_parts.wav`（方式 C）は打ごとに元の音の特徴で代表音を選ぶので、MIDI に無い情報を使っている。表の「STFT（MIDI だけで鳴らす）」がその距離。`--parts nmfd` のときは `hits_model.mid`（`--tag v5` なら `hits_model_v5.mid`）に、この鳴らし方に合わせた強さの付いた打点が入る。`--save-kit kit` で保存したキットと合わせて、プラグインで同じ音が鳴る（6 節）。
- `--parts nmfd` では、採譜の打点のうち、分けたパートに音の無いもの（その種類の大きい打より 40 dB 以上小さい）を除く。表の「音が無くて除いた打」がその数、「F（MIDI にした打点）」が除いた後の F 値。
- 表の「種類ごとの距離」は、その種類だけを鳴らした音と、そのパートの音（キットを切り出した元）との距離。`ki0.28/0.25/0.03` は キックの「MIDI だけ／方式 C／自己再現」。混ざった音の距離では、キックやスネアの違いはハイハットやシンバルの差に埋もれるので、「MIDI だけだとキックが悪い」のような聞こえ方はこの列で見る（MIDI だけが方式 C より大きい種類）。
- 表の「MIDI だけの損失の内訳」は、その種類だけを自己再現（その打自身の音）に置き換えたときに、混ざった音の距離がどれだけ下がるか。大きい種類が、MIDI だけで鳴らしたときに元から遠い種類。「位置が 5 ms 以上ずれる打の割合」は、MIDI の時刻に置いた代表音を、その打の元の音に相互相関で合わせ直したときに 5 ms より大きく動く打の割合（種類別）。0 に近いほど、打点の時刻と音の頭がそろっている（目安。正解の時刻で確かめると、本当にずれた打の 4〜8 割を拾い、ずれていない打も数 % 数える）。
- `--save-kit kit` と `kit_parts_audition.wav` は、MIDI 用のキット（音量の順に区分し、各区分から普通の音を選んだもの。2026-11-17 から）。方式 C の距離（`rerender_parts.wav`）は、従来どおり特徴の k-means の代表音で測る。`rerender_midi_km.wav` は、同じ打点を従来のキット（k-means の代表音）で鳴らしたもの（表の「STFT（MIDI だけ、k-means のキット）」）。キットの選び方だけを聞き比べられる。
- `rerender_midi_k48.wav` は、代表音を種類ごとに 48 音（既定は 24 音）にして同じ MIDI で鳴らしたもの。表の「STFT（MIDI だけ、代表 48 音）」がその距離。既定の音の数を決める材料。
- 表の「分離の確からしさ」は、種類ごとの中央値（0〜1）。自前のパート分け（`--parts nmfd`／`nmfd-oracle`）で、その打の時刻・帯域がそのパートの音だけなら 1 に近く、他の音と重なっていると小さい（スネアと同時に鳴ったハイハットなど）。0.8 未満の打からは、キットの代表音を取らない（取り出した音の大半が別の太鼓の音になるため）。
- `--render` で各曲のフォルダにできる WAV: `original_cut.wav`（元）、`rerender_self.wav`（各打をその打自身の区間で鳴らし直し。打点と区間の切り方だけの損失）、`rerender_parts.wav`（方式 C: 特徴で選んだ代表音を各打に最も近いものから選び、音量と立ち上がりの位置を合わせ、同じ種類の次の打で止める）、`rerender_parts_embed.wav`（方式 D: 先頭 0.25 秒の対数メルの埋め込みで選ぶ）、`rerender_parts_3x3.wav`（方式 A: 3 層 × 3 音のキット、従来）、`rerender_mix.wav`（混ざったドラムから切り出したキット）、`kit_parts_audition.wav`（MIDI 用のキットの音を 種類 → 弱→強 の順に並べたもの）。方式 B（A ＋ 音量合わせ ＋ チョーク）は表の数字だけ。`--kit-size` で方式 C の種類ごとの音の数（既定 24。`all` で全部を代表にする）、`--choke all|hihat|none` で `rerender_parts.wav` のチョークの方針（表には 3 通りの距離が出る）、`--only a01,a07` で曲を絞って速く試せる。`--parts nmfd` でパート別ステムの代わりに自前の NMFD（推定の打点が初期値）でパートを分け、同じ表を出す（製品の経路。SpectraLayers のパートがあれば SNR の列が出る。`nmfd_<種類>.wav`）。`--parts nmfd-oracle` は疑似正解の打点を初期値にして NMFD を動かす（採譜の誤りを除いた、分離の上限）。`--nmfd-no-residual` は NMFD の残差の成分を使わない（パートの和が元に等しくなる。取りこぼした打の音も最も近いパートに入る）。`--nmfd-legacy` は 2026-11-15 より前の NMFD（打点の後の音がパートから消える不具合のある版。直す前後の比較用）。表の「パートの出どころ」の列にどれで測ったかが出る。表の「帯域の差」の 3 列は、パートの和・自己再現・方式 C を元と比べた帯域ごとの差（dB。低 200 Hz 未満、中低 〜1 kHz、中 〜4 kHz、高 〜10 kHz、超高）。再現の列は音量をそろえた後の差で、高・超高が負なら「こもる」、中低・中が負なら「痩せる」。`--model` に `{id}` を含めると曲 ID に置き換わる（微調整の曲ごとのモデル。`"analysis\models\crnn_ft_v5_{id}.onnx"`。`E-GMD学習の手順.md` 5 節）。`--save-kit kit` で MIDI 用のキット（製品のキット）を曲フォルダの `kit\` に保存し、プラグインの「kit.json を読む」で鳴らせる。`--fit-fx` で M0-3 を実ステムで測る（合成キットの乾いた音に固定チェーンを当てはめ、前後の距離。1 曲 2〜3 分。`synthkit_dry.wav`／`synthkit_fx.wav`）。表の末尾に曲ごとの「悪い区間」（方式 C の距離が大きい 2 秒窓と、そこでの自己再現の距離・種類別の打数）が出る。自己再現も悪ければ打点（疑似正解や分離）側、自己再現が良ければ代表音の不足。`--render` では `timeline.csv`（1 秒ごと）も書く。

## 5. 聞き比べ用の WAV を作る（M0-2）

曲ごとに、切り出したキットで鳴らし直した WAV を作る。

```
python analysis\baseline_transcribe.py data\stems\a01\drums.wav data\stems\a01\est.csv
python analysis\extract_kit.py data\stems\a01\drums.wav data\stems\a01\est.csv data\stems\a01\kit --render data\stems\a01\rerender.wav
```

`drums.wav`（元）と `rerender.wav`（再現）を交互に聞いて、「同じキットに聞こえる／違う」を `docs\phase0\M0判定.md` の表に書く。切り出した音は `kit\` に層ごとの WAV で入る。

## 6. 1 曲を解析して、プラグインで鳴らす

`analyze_stem.py` は、ドラムのステム 1 本からキットと MIDI を作る（製品の解析と同じ経路。評価の表は出さない）。

```
python analysis\analyze_stem.py data\stems\a04\drum.wav data\kits\a04 --model analysis\models\crnn_egmd_v5.onnx --start 71 --seconds 60 --preview
```

- `data\kits\a04\` に、`kit.json` と種類ごとの WAV（キット）、`hits.mid`（打点。時刻は元のステムの先頭から、120 BPM）、`analysis.json`（打の数、強さと音量の対応、所要時間）ができる。
- `--preview` を付けると、`preview_midi.wav`（このキットを `hits.mid` だけで鳴らした音）と `original_cut.wav`（同じ区間の元の音）も書く。まずこの 2 つを聞き比べる。
- `--start` は解析を始める位置（秒。`run_eval.py` の表の「開始秒」か `start.txt` の値）、`--seconds` は長さ（省略すると最後まで）。3 分の曲の全部で、パート分けに 30 秒前後かかる。
- プラグインで鳴らす: DAW で `DrumSamplerPlugin`（VST3。GitHub Actions の `build` の成果物 `DrumSamplerPlugin-windows-vst3`）を立ち上げ、「kit.json を読む」で `data\kits\a04\kit.json` を選ぶ。
  DAW のテンポを 120 BPM にして `hits.mid` をそのトラックの先頭に置き、元のステム（`drum.wav`）を別のトラックの先頭に置く。2 つを切り替えて聞き比べる。
  プラグインの音は `preview_midi.wav` と同じになる（Python と C++ のエンジンが同じ音を出すことは CI で確かめている）。
- v5 のモデルは CD 曲のステムを学習の増強に使ったので、評価用に限る（製品には入れない）。

## 困ったとき

- `git pull` が「untracked working tree files would be overwritten」で止まる → 手元で作ったファイルがこちらのコミットと同名。そのファイルを `data\` に移してから `git pull`。

- `python` が見つからない → Python のインストーラーで PATH のチェックを忘れている。再インストールするか、`py -3` を `python` の代わりに使う。
- `pip install` で `mir_eval` や `soundfile` が失敗する → `python -m pip install --upgrade pip` の後にやり直す。
- `run_eval.py` が「drums.wav のあるフォルダが見つからない」と言う → フォルダ名とファイル名（`drums.wav` か `drums.flac`）を確かめる。
