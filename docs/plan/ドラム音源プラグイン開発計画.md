## 1. 結論（先に要点）

1. **仕様の中心「ステムからキットを自動で組み、エフェクトまで再現する」は、D3 で見つけた空白地帯（仮説1）にそのまま重なる。** 市販品は「一打を検出して置き換える」（Superior Drummer 3 の Tracker、Drumagog など）までで、ステムから音色とエフェクトを推定して編集できるキットにする製品は、調べた範囲では見つからなかった。ここを製品の顔にする。
2. **解析は「採譜 → パート分け → 一打の切り出し → 3通りのキット候補 → エフェクトの当てはめ」の5段で組む。** 解析はすべてオフライン（読み込み時に裏で計算）にし、音を鳴らす側の実時間処理と切り離す。
3. **音源方式はハイブリッド。** サンプル再生（ステムから切り出した音・内蔵ライブラリ）を土台に、キック・スネア・タムはモーダル合成（D2 の選択肢1〜3）を並べる。シンバルは当面サンプルで、非線形の板（D3 仮説2）は v1.0 の後の差別化テーマに回す。
4. **「全機能網羅」はそのままでは個人開発で達成できない。** 32機能を A〜D の4段に分け、A（仕様の中核）と B（v1.0 までに入れる）で 25機能、C は v1.x 以降、D（11.1サラウンド、数百GBのマルチマイク収録など）は「別の方法で同じ目的を満たす」か「やらない」とする（4章）。網羅の度合いは既存の機能マトリクスに自社列を足して測る。
5. **展開の生成は、まずルールの組み合わせ（変換レシピ）で作り、機械学習は後から足す。** ルールなら結果を説明でき、利用者が直せる。学習モデルは曲の区間ラベル付きのデータが足りないことが最大の壁（6章）。
6. **フェーズは 0〜5。** 技術検証（Phase 0）で「採譜の精度」「切り出した音の質」「エフェクトの当てはめの効き」を数字で確かめ、続けるか判断する。v1.0（Windows VST3）までの見込みは 12〜16 か月。
7. **最大のリスクは、①分離済みステムの音質（にじみ・他楽器の混入）、②エフェクトと元の音色が数学的に一意に分けられないこと、③市販曲から切り出した音の扱い（著作権）。** ②は「正解を当てる」ではなく「聞いて同じに聞こえ、後から直せる」を目標に置くことで扱う（8章）。

## 2. 全体構成

```
[ドラムのステム（WAV）]
      │  読み込み（ドラッグ＆ドロップ）
      ▼
┌──────────── 解析（オフライン・裏のスレッド） ────────────┐
│ ① 前処理      テンポ・拍の推定（ホストのテンポがあれば優先）        │
│ ② 採譜        打点の時刻・種類・強さ → MIDI                       │
│ ③ パート分け  キック／スネア／タムの本数と音程／ハイハット／シンバル  │
│ ④ 一打の切り出し  重なりの少ない打を選び、強さ別・ラウンドロビン別に │
│ ⑤ キット候補  (a) 切り出した音 (b) 内蔵ライブラリの近い音          │
│               (c) モーダル合成のパラメータの当てはめ               │
│ ⑥ エフェクトの当てはめ  パートごとの EQ・コンプ・歪み・ゲート、      │
│                       共通のリバーブ・定位                         │
└─────────────────────────────────────────┘
      │  結果はプロジェクトに保存（再解析しなくてよい）
      ▼
┌──────────── 実時間の音源 ────────────┐
│ ボイス: サンプル／モーダル（パートごとに切替・混合） │
│ パートごとの FX チェーン → バス → マスター           │
│ シーケンサー（基準パターン＋曲の展開）             │
└───────────────────────────────┘
      │
      ▼
 DAW へ: ステレオ／個別出力、MIDI のドラッグ書き出し、オーディオの書き出し
```

画面上では、③の結果がキットの絵に自動で並び（仕様1）、⑤⑥の結果が各パートの音色とエフェクトとして入る（仕様2）。元のステムと再現した音を A/B で聞き比べられることを、全工程の確認手段にする。

## 3. 技術の選択

### 3.1 入力と前処理

- 入力は仕様どおり「分離済みのドラムのステム」。分離の道具（Demucs〔MIT〕、Serato、各 DAW の分離機能など）は利用者が選ぶ。曲全体からの分離を内蔵するのは Phase 5 以降の選択肢（F30。Serato Sample と Maschine 3 は持っている）。
- テンポと拍はホスト（DAW）から受け取るのを優先し、無ければ拍の推定（ビートトラッキング）で求める。小節の頭がずれると展開の生成（6章）がすべて崩れるので、画面で1拍目を直せるようにする。

### 3.2 採譜（打点の時刻・種類・強さ）

- **方式**: 自動ドラム採譜（ADT）の学習モデル（CNN＋RNN、または小さな Transformer）を PyTorch で学習し、ONNX 形式に書き出してプラグインの中で ONNX Runtime（MIT）で動かす。研究では CRNN 系が標準的な手法。
- **分類の粒度**: 研究や公開データの多くは3〜5種類（キック・スネア・ハイハット・タム・シンバル）。仕様のためには、ハイハットの開閉、スネアのリムショット／サイドスティック、タムの本数、ライド／クラッシュ／チャイナの区別が欲しい。段階的に増やす。
  - Phase 1: キック／スネア／ハイハット（閉）／タム／シンバル の5種
  - Phase 2: ハイハット（開・ペダル）、ライド（ボウ・ベル）、クラッシュ、リム。タムの本数と音程は、タムと判定した打を音程でまとめる（クラスタリング）
- **学習データの候補（ライセンスは 2026-10-23 に確認。`docs/phase0/ライセンス一覧.md`）**: E-GMD（電子ドラムで録った大規模データ、CC BY 4.0）、Groove MIDI Dataset（Magenta、CC BY 4.0）、StemGMD（パート別に分けたドラムの合成データ、CC BY 4.0。LarsNet の論文と同時に公開）は学習に使える（表示義務）。ADTOF（実曲と音楽ゲームの譜面から作った大規模データ）はデータが内部の非商用利用のみ、コードと学習済みモデルが CC BY-NC-SA 4.0 なので評価・比較にだけ使う。2026年には「実曲に近い合成データで学習する」研究（arXiv 2601.09520）も出ており、**自社のサンプルとモーダル音源で合成データを作って学習する**道が、権利の面で最も安全。
- **分離済みステム特有の対策**: 分離のにじみ・他楽器の残りを入れて学習時に音を汚す（データ拡張）。
- **強さ（ベロシティ）**: 打点ごとの立ち上がりの大きさを、パートごとの分布で 1〜127 に割り当てる。エフェクトのコンプで強さの差が潰れている場合があるので、6.の当てはめの後でもう一度補正する。

### 3.3 パートの分解（必要な場合）

- 重なった打（キックとハイハットが同時など）から一打を取り出すには、ドラムのステムをさらにパート別に分けるとよい。
- 候補は2つ。(1) LarsNet 型の学習モデル（キック・スネア・タム・ハイハット・シンバルの5つに分ける。StemGMD で学習。データは CC BY 4.0、公開の学習済みモデルは CC BY-NC 4.0 なので製品には自前で学習し直す。コードのライセンスは要確認。2026-10-23 確認、`docs/phase0/ライセンス一覧.md`）。(2) 学習を使わない NMFD（非負値行列因子分解の畳み込み版。採譜の結果を初期値にし、パートごとのひな形を当てはめる）。
- 方針: Phase 0 で両方を試し、軽くて権利が明確な (2) を先に入れる。(1) は自前のデータで学習し直す前提。

### 3.4 一打の切り出しとキット候補（仕様1・2の音色側）

各パートについて、次の3つを作り、利用者がパートごとに選ぶか混ぜる。

| 候補 | 作り方 | 長所 | 短所 |
|---|---|---|---|
| (a) ステムから切り出した音 | 採譜の結果から「前後に他の打が重ならない打」を選ぶ。強さで3〜5層に分け、同じ層の中の複数の打をラウンドロビンにする。尾は次の打で切れるので、モーダル合成か減衰の当てはめで延長する | 元の音そのもの。エフェクト込みで最も似る | 分離のにじみが残る。打が少ない曲では層が作れない。シンバルは尾が重なり切り出しにくい |
| (b) 内蔵ライブラリの近い音 | 一打の音を特徴ベクトル（埋め込み）にし、ライブラリの中で近い音を探す（XO・Atlas 2 の「似た音の地図」と同じ考え方を検索に使う） | きれいな音。強さの層とラウンドロビンが揃う | ライブラリの量と質に左右される。個人開発では収録の量に限界 |
| (c) モーダル合成のパラメータ | 一打の音からモードの周波数・減衰・振幅を推定し、膜のモデル（張り・大きさ・材質・打点・張力の変調）に当てはめる（D2 の選択肢11、D3 の仮説1） | 軽い。張り・材質・打点を後から変えられる（他製品に無い） | 実録音での推定は研究段階。張りと大きさを分けるには曲げ剛性・空気・減衰まで含むモデルが要る（D3） |

- 初期値は (a) を使い、(a) の質が低いと判定したパート（打が少ない、にじみが大きい）は (b) を出す。(c) は Phase 2 で入れ、v1.0 の時点では「音色を後から作り変える」ための上級機能と位置づける。
- 質の判定には、切り出した音と元のステムの該当部分の差（多重解像度の STFT 距離）と、打の数・重なりの割合を使う。画面には「信頼度」として出す（低いパートを色で知らせる）。

### 3.5 エフェクトの推定（仕様2のエフェクト側）

- **考え方**: 「乾いた音＋エフェクト ≒ ステムの音」になるように、決まった形のエフェクトチェーンのパラメータを最適化する（合成による分析、analysis-by-synthesis）。研究では微分可能な信号処理でエフェクトのパラメータを推定する DeepAFx-ST（Steinmetz ら、2022）や、推論時に最適化する方法がある。
- **チェーンの形（固定）**
  - パートごと: 入力の音量 → EQ（ローカット、3〜4バンドのピーキング、ハイシェルフ）→ コンプ（閾値・比・アタック・リリース）→ 歪み（テープ／真空管の近似）→ ゲート（必要なパートだけ）
  - 共通: リバーブ（部屋の大きさ・減衰時間・初期反射・高域の減衰。ルーム／プレート／ホールの3型から選ぶ）、パートごとのセンド量と定位、マスターのバスコンプ
- **推定の手順**
  1. 乾いた音の基準を決める。(b) のライブラリの音、または (c) のモーダル合成の音を「エフェクト前」とみなす。(a) の切り出した音は既にエフェクトが掛かっているので、(a) を使うパートは EQ・コンプを中立にし、リバーブの尾の延長だけを推定する。
  2. 減衰の形とスペクトルの包絡から、リバーブの減衰時間と EQ をまず解析的に求める（初期値）。
  3. 微分可能なエフェクトの近似（PyTorch で書く）で、多重解像度の STFT 距離が小さくなるようにまとめて最適化する。
  4. 結果を、プラグイン内の実際のエフェクトのパラメータに写す（近似と本物の特性の差は、事前に表で補正）。
- **大事な限界**: 「音色」と「EQ」、「元の減衰」と「コンプの効き」、「部屋の響き」と「リバーブ」は、録音だけからは一意に分けられない。目標は「正解の設定を当てる」ではなく「聞いて同じに聞こえ、普通のエフェクトとして後から直せる」にする。評価も聞き比べと STFT 距離で行う。
- 推定の計算は Phase 0〜1 では Python で行い、プラグインに入れる段階で C++ の最適化（勾配を使わない方法、または ONNX にした推定用の小さなモデル）に移す。

### 3.6 音源方式

| 方式 | 使う場所 | 根拠 |
|---|---|---|
| サンプル再生 | 全パート（切り出した音、内蔵ライブラリ、利用者の音） | 仕様1・2で「元の音」に最も近づける唯一の方法。F21（自前サンプル）・F22（差し替え）も同じ仕組みで満たせる |
| モーダル合成（線形＋張力の変調＋ビーターの衝突＋空気の結合・響き線の簡易版） | キック・スネア・タム | D2 の結論: 個人開発・JUCE で実時間の土台にしやすい。計算量はモード数に比例。D2 の選択肢1→2→3の順で作る |
| モード合成の板 → 将来は非線形の板（von Kármán） | シンバル・ゴング（v1.x 以降） | D3 仮説2。市販プラグインは見つからなかったが、計算量と安定性が難しく、Physical Audio が先行しうる |
| アナログ風の合成（Microtonic・Spark 型） | 電子系のキット（808 など） | 機能 F17 の網羅のため。オシレーター＋ノイズ＋エンベロープで軽く作れる |

- 各パートは「サンプル層」と「合成層」を持ち、比率で混ぜられるようにする（BFD3 の Tech／Model、DrumComputer の3層の考え方）。
- 内蔵ライブラリは、自分で録るか、権利を買ったワンショットで小さく作る（数GB程度を想定）。Superior Drummer 3（230GB超）のような量は狙わない。量の代わりに「モーダル合成で調整できる」ことで幅を出す。
- OSS の扱い（D1・D2 から）: STK（MIT 形式）、Mutable Instruments のファームウェア（MIT）、Faust の生成コード（例外つき）は組み込める。RipplerX・Kit・nlm などの GPL 系は読んで仕組みを学び、自分で書き直す。

### 3.7 フレームワークと構成

- **JUCE（C++、CMake）**。VST3 を Windows で最初に出し、AU と macOS は Phase 5。CLAP は clap-juce-extensions で後から足せる（要確認）。JUCE は AGPLv3 と商用ライセンス（EULA）の二本立て。JUCE 8 の無料階層 Starter（年 $20,000 まで）はスプラッシュ画面不要、超えたら Indie（$40/月か $800 買い切り、$300,000 まで）（2026-10-23 確認、juce.com/get-juce）。VST3 SDK は 3.8（2025-10-29）以降 MIT で、閉じたソースの配布に契約の署名も料金も不要。JUCE 8.0.15 の同梱 SDK は 3.8.0（2026-10-23 確認、github.com/steinbergmedia/vst3sdk の LICENSE.txt と README）。VST の商標・ロゴを使うなら Steinberg のガイドラインに従う。詳細は `docs/phase0/ライセンス一覧.md`。
- **機械学習の推論**: ONNX Runtime（MIT）を裏のスレッドで動かす。音を鳴らすスレッドでは推論しない。モデルは数十MB以内を目標にする。
- **モジュール**
  - `Analyzer`（オフライン解析。採譜・分解・切り出し・推定。進み具合を画面に出し、途中で止められる）
  - `KitModel`（キット・パート・層・FX 設定のデータ。プロジェクトの状態として保存）
  - `Engine`（ボイス管理、`SampleVoice`・`ModalVoice`・`SynthVoice`、チョークとハイハットの開閉、FX チェーン、バス、個別出力）
  - `Sequencer` と `Arranger`（基準パターン、区間、展開の生成、ホスト同期）
  - `UI`（5章）
- **保存**: 解析結果と切り出した音をプロジェクト（プラグインの状態）に含めると DAW のプロジェクトが重くなるので、切り出した音は利用者のフォルダに書き出して参照する方式も選べるようにする。
- **品質の確認**: pluginval で VST3 の動作を自動検査、GitHub Actions で Windows と macOS のビルド、解析の精度は固定の評価用ステム集で毎回測る（回帰テスト）。
- **開発の順序**: 解析は Python（PyTorch、librosa など）で試作して精度を確かめてから C++／ONNX に移す。音源側は最初から JUCE で書く。

## 4. 「既存製品の全機能網羅」の優先順位

### 4.1 方針

- 「網羅」を「既存製品の各機能が満たしている**目的**を、このプラグインでも満たす」と読み替える。実装の仕方は同じでなくてよい（例: マルチマイク収録の代わりに、仮想マイクの位置と部屋のシミュレーションで F11・F12 を満たす）。
- 網羅の度合いは、既存の `ドラム音源_機能比較.xlsx` の「製品×機能」シートに自社の列を足し、フェーズごとに ○／△ を付けて測る（生成スクリプト `scripts/build_feature_matrix.py` に追記）。
- 優先順位の決め方: (1) 仕様の4項目に直接かかわるか、(2) 25製品のうち何製品が持っているか（よくある機能は無いと不満になる）、(3) 個人開発でかかる手間。

### 4.2 32機能の振り分け

| F23 サンプルの自動整理・分類 | 解析のパート分けがそのまま当たる |
| F21 自前サンプルの読み込み | 切り出した音を鳴らす仕組みと同じ |

## 5. UI の整理方針（「ごちゃごちゃしない」ために）

### 5.1 原則

1. **作業の順に4画面に分ける。** 1画面で1つの作業だけをする。上部のタブで切り替える。
   - ① **解析**（読み込み）: ステムを落とす → 進み具合 → 結果の一覧（パートと信頼度）→ 採譜の修正
   - ② **キット**: キットの絵。パートを押すと右側の詳細欄が切り替わる
   - ③ **ミックス**: パートごとの音量・定位・FX、バス、仮想マイク
   - ④ **展開**: 基準パターン、区間（Intro／Verse／Chorus…）の並び、候補の比較
2. **段階的に見せる。** 詳細欄は「基本（3〜6個のつまみ）」が初期表示で、「詳しく」を開くと全パラメータ。例: スネアの基本は「音程・減衰・明るさ・響き線・部屋の量」、詳しくは「張り・大きさ・材質・打点・張力の変調・空気…」。
3. **詳細欄は1つだけ。** どの画面でも、選んだもの（パート、FX、区間）の設定は右側の同じ場所に出す。浮き窓や入れ子のダイアログを作らない。
4. **元の音と比べられる。** 全画面の上部に「元のステム／再現」の A/B ボタンと、同じ位置で再生する仕組みを常に置く。再現の確からしさが分かることが、この製品の信頼の元になる。
5. **自動の結果は「提案」として出し、直せる。** 信頼度の低いパートは色で知らせ、候補 (a)(b)(c) を切り替えて聞ける。どの操作も元に戻せる（履歴）。
6. **用語をそろえる。** 物理量（張り・材質）と、エンジニアの用語（EQ・コンプ）を混ぜない。キット画面は「楽器の言葉」、ミックス画面は「エンジニアの言葉」に分ける。

### 5.2 確かめ方

- Phase 3 の終わりに紙またはFigmaの試作で、Phase 4 に実物で、5人程度に課題を出して使ってもらう（例:「このステムを読み込み、スネアだけ明るくして、Chorus を2種類作って DAW に書き出す」）。迷った場所と時間を記録して直す。
- 機能が増えるたびに「基本の表示に出すつまみの数」の上限（例: 6個）を守っているかを確認する。

## 6. 基準パターンから曲の展開を作る方式（仕様4）

### 6.1 入力と出力

- 入力: 基準パターン（1〜4小節。採譜の結果から選ぶか、打ち込む）、テンポ・拍子、作りたい区間の並び（例: Intro 8小節 → Verse 16 → Chorus 16 …）。
- 出力: 区間ごとに複数（例: 3〜5）の候補。利用者が選び、並べ、直す。MIDI として DAW に書き出せる。

### 6.2 段階1: 変換レシピ（ルールの組み合わせ。Phase 3）

区間ごとの「性格」を、基準パターンに掛ける変換の組み合わせとして定義する。

| 変換 | 例 |
|---|---|
| 密度 | ハイハットを8分→16分、キックの裏拍を足す／抜く |
| 楽器の置き換え | ハイハット→ライド（Chorus）、ハイハット→リム（Verse の静かな部分） |
| 要素を抜く | Intro はキックとハイハットだけ、Breakdown はキックを抜く |
| 強さ | ベロシティの全体の高さと幅（Chorus は強く、Verse は弱く） |
| 拍の感じ | ハーフタイム／ダブルタイム |
| 区間の頭と終わり | 頭にクラッシュ、最後の1〜2拍にフィル（長さと複雑さを選ぶ） |
| 揺れ | 元のステムのマイクロタイミングとアクセントを残す |

- 各区間の既定のレシピ（Intro／Verse／Pre-Chorus／Chorus／Bridge／Breakdown／Outro）を用意し、ジャンル別の設定（rock、lo-fi、EDM、psybient など。機能比較の「ジャンル別キット」シートの関心に対応）で変える。
- 候補を複数出すために、各変換に確率と乱数の種を持たせる。候補は「基準との近さ」（リズムの類似度）と「候補どうしの違い」で並べ、似すぎ・離れすぎを除く。
- 長所: 結果の理由を説明でき、つまみで直せる。学習データが要らない。

### 6.3 段階2: 学習モデル（Phase 5）

- 基準パターン・区間の種類・強さを条件にして、パターンを生成する小さなモデル（VAE または Transformer。Magenta の GrooVAE の考え方）を学習し、ONNX でプラグインに入れる。
- **データの壁**: ドラムの MIDI のデータ（Groove MIDI Dataset、E-GMD など）には、Intro／Verse／Chorus のような区間のラベルがほとんど無い（要確認）。対策の候補: (1) 曲全体の MIDI に構造の解析（自己類似度）でラベルを付ける、(2) 自分で区間ラベル付きのデータを作る、(3) ラベルを使わず「強さ・密度」の条件だけで生成し、区間の性格は段階1のレシピで与える。(3) が最も確実。
- 段階1のレシピは捨てず、学習モデルの出力を整える後処理としても使う。

## 7. フェーズとマイルストーン

期間は個人開発で週20〜30時間を仮定した筆者の見込み。

| フェーズ | 期間（目安） | 内容 | 終わりの判定（マイルストーン） |

## 8. リスクと対策

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| R1 | 分離済みステムの音質（にじみ、ベース・ボーカルの残り、シンバルの尾の欠け） | 切り出した音が汚い。採譜の誤り | データ拡張で学習、NMFD で重なりをほどく、信頼度が低いパートは (b)(c) を出す |
| R2 | 音色とエフェクトを一意に分けられない | 推定した EQ・コンプが「本物の設定」と違う | 目標を「同じに聞こえ、直せる」に置く。聞き比べで評価。説明書でも正直に書く |
| R3 | 市販曲から切り出した音の扱い（著作権） | 利用者が切り出した音をプリセットとして配ったり、製品にその音を同梱したりすると問題になりうる | 製品には市販曲から切り出した音を一切同梱しない。切り出しは利用者の手元だけで行い、共有機能では音を含めない設定を既定にする。宣伝で特定の曲名・アーティスト名を使わない。発売前に専門家に確認（法的な判断はこの計画の範囲外） |
| R4 | 学習データとモデルのライセンス | 商用の製品に使えない | Phase 0 で一覧を作り確認。最も安全なのは、自社のサンプルとモーダル音源で作る合成データ |
| R5 | 採譜の細かい分類の精度（ゴーストノート、ハイハットの開き具合、タムの区別） | キットの割り当てを間違える | 段階的に分類を増やす。修正の UI を早く作る |
| R6 | 「全機能網羅」の範囲が膨らむ | 発売が遅れる | 4章の A〜D を守り、追加の要望は C に入れて次の版で判断 |
| R7 | CPU 負荷（モーダルの声数、FX チェーン×パート数） | DAW で重い | モード数を可変にする、使っていない FX を止める、SIMD（AVX2）。解析はオフラインに限る |
| R8 | 競合の追随（Toontrack などがステムからキットを作る機能を出す、Physical Audio が非線形の板を製品化） | 差別化が薄れる | 早くアルファを出す。物理パラメータで作り替えられる点（候補 (c)）を独自性として育てる |
| R9 | 特許 | 録音から材質を推定する米国特許（UNC、US 9,401,684 B2）が D3 で見つかっている。導波管の特許の注記（STK） | Phase 2（推定を入れる前）に、請求項と権利の状態を確認する。日本の特許は未調査（D3） |
| R10 | 個人開発の時間 | 全体が延びる | フェーズの終わりの判定で範囲を削る。解析の学習は外部の計算資源（クラウドの GPU）を短期で借りる |
| R11 | JUCE・コピープロテクトの費用と条件 | 販売時の費用 | JUCE は売上 $20,000 までは無料、超えたら Indie $800 買い切り（2026-10-23 確認）。VST3 SDK は MIT になり費用なし。コピープロテクトは Phase 4 の前に条件を確認して予算に入れる |
