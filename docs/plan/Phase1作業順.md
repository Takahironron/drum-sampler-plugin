# Phase 1（MVP「ステム → 鳴るキット」）の作業順

- 作成日: 2026-11-03
- 前提: M0 判定（`docs/phase0/M0判定.md`）は「続ける」で確定。M0-2・M0-3 は合格、M0-1 は 0.77（目安 0.85）で未達。
- Phase 1 の目標（計画書 7 章）: **M1（内部アルファ）= ステムを落として 1 分以内（3 分の曲）にキットが鳴り、MIDI で DAW に渡せる。** 期間の目安 3〜4 か月（根拠のある数字ではない）。
- 内容（計画書）: 解析 ①〜④（5 種の採譜、切り出し、自動の割り当て）、サンプルのエンジン、チョーク、パートごとの簡単な EQ・コンプ、A/B 比較、採譜の修正、MIDI の書き出し、個別出力。

## 1. 方針

1. **製品の経路を先に通す。** Phase 0 の M0-2 は SpectraLayers のパート別ステムと、その打点検出に依存していた。製品では「採譜 → パート分け → 切り出し」を自前で行う必要があるので、最初の 2 週間でこの経路を Python で通し、SpectraLayers のパート別ステムを**正解の代わり**にして測る（分離の質の物差しが手元にある）。
2. **Python で出た `kit.json` を JUCE で鳴らす形から始める。** 解析を C++ に移す前に、Python の出力（キットの JSON と WAV、打点の MIDI）をプラグインが読んで鳴らせれば、M1 の形が早く見える。C++／ONNX への移植はその後。
3. **採譜の改善は並行して、E-GMD の全データと区分 B で。** Phase 0 の持ち越し 1。GPU の学習は夜に回す。

## 4. Phase 0 から持ち越した課題（`docs/phase0/M0判定.md` の順）

1. 採譜の小さい打（ハイハット 0.68、スネア 0.87。E-GMD 全データ、ゴーストノートの別扱い、公開モデルとの比較、区分 B での実測、検証と test の差の原因）。
2. パート分けの自前化（最重要。NMFD か StemGMD の学習モデル）。
3. 打点で説明できない音（タンバリン、残響）の扱い。「その他のパーカッション」か「残差の層」。
4. エフェクトの当てはめの乾いた音の基準（内蔵ライブラリ、モーダル音）とチェーンの範囲（コンプ・歪み・ゲート）。
5. 代表音の選び方の天井（特徴の設計か、聞こえ方に沿った距離の指標）。製品の経路ではシンバルが損失の最大（過検出と、長い余韻の代表音。2026-11-13）。
6. 採譜が取りこぼした打を、その曲のひな形で拾い直す（NMFD の活性からの二段目の検出）。同じ種類の取りこぼしは前の打の区間に含まれ、代表音に 2 度打ちが混ざる恐れがある（2026-11-15）。
7. ステムに残ったにじみ。NMFD では取り除けず、スペクトルの近いパートに入る（2026-11-15。ステムの分離の側の課題）。
8. スネアと同時に鳴るハイハット、ライドとクラッシュの分け方（NMFD の限界。足りなければ StemGMD で学習するモデル）。
9. v5 の実ステムでのハイハットとシンバルの取りこぼし（ハイハットの検出 1617 対 疑似正解 2975、シンバル 39 対 1929。ハイハットの疑似正解は正確なので本物）。直した疑似正解での微調整か、持ち越し 6 の二段目の検出で埋める。
10. 疑似正解に頼らない物差し。区分 B（正解 MIDI 付き）を揃える。疑似正解は、ごく弱いゴーストノートを落とし、漏れの大きいステムではまだ数え過ぎる。
11. **E-GMD の正解の時刻のずれ**（2026-11-16）。配布物の MIDI と音が、ファイルごとに一定量ずれている（標本 67 本: 10 ms 以上 34%、30 ms 以上 15%、50 ms 以上 7%、−73〜+119 ms。test 分割の標本は 14 本中 5 本が 30 ms 以上）。採譜モデルの学習（v1〜v5）と E-GMD での採点は、このずれたラベルを使っている。測って直す道具はできた（`analysis/egmd_offsets.py`）。全データでの測定、v5 の採点し直し、直したラベルでの v6 の学習が残る（Takahiro の PC）。M0-1 の「0.77」と、検証と test の差（持ち越し 1）は、これで説明できる恐れがある。
12. 同時に鳴る打での分離（2026-11-16）。スネアと同時のハイハットは、取り出した音の約半分が別の音（SN 比 +2.4 dB）。代表音からは外したが、打の強さは狂う。ハイハットのパートそのものが弱い（本当の録音との距離 1.37。キック 0.23、スネア 0.41）。持ち越し 8 と同じ根。
13. 奏法の分類（ハイハットの開閉、ライドとクラッシュ、タムの高さ）を別の MIDI ノートにする。特徴の k-means では奏法を見分けられなかった（文脈で分かれる）。Phase 2 の「細かい分類」で、正解のある学習で行う。
14. MIDI だけで鳴らすと、方式 C より遠い（区分 A で 1.70 対 1.32、2026-11-17。合わせ直しを直す前）。直した後、クラウドの標本ではキックとスネアは方式 C と同じ程度で、残る差はハイハットの選び方（持ち越し 13）。代表音を 48 音にしても、Takahiro の耳では変わらなかったので、既定は 24 音のまま。MIDI 用のキットは各音量帯の普通の音を選ぶぶん、超高域が 0.3〜1 dB 下がる（開いたハイハットなどの明るい打の分）。耳で気になるかは聞き比べ待ち（`rerender_midi_km.wav` と比べる）。
15. 打点の時刻の精度（2026-11-17）。キックは直した（5 ms 以上ずれる打が 11% → 1%）。残るのは、小さいスネア（ゴーストノート。E-GMD で 3 割がずれる）、隣の打が 60 ms 以内にある打、スネアと同時に鳴るハイハット。ずれは、ひな形との相関が低い打に集まる（`refine_onsets` の `stats`。信頼度表示の材料）。ハイハットは、分離の窓による前ぶれのぶん、打点が数 ms 早く出る（種類の中では一定）。
16. ONNX Runtime のテレメトリ（2026-11-17）。公式の配布物は、利用状況（OS、CPU、実行したプログラムの名前、端末の識別子のハッシュ）を Microsoft に送る機能が既定で有効。今は初期化の前に環境変数で切っている。製品では、テレメトリ無しの自前ビルド（`--no_telemetry`）にするかを販売前に決める。同梱する `onnxruntime.dll` の置き方（DAW のプロセスに他の版が読み込まれているときの衝突）も未確認。
